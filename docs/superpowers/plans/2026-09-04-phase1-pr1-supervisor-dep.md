# Phase 1 PR 1 — Supervisor Dependency Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land `supervisor==4.3.0` as a pinned main dependency, alone, so `base-image.yml` rebuilds
`ghcr.io/…:base` with supervisord on `main` before any later PR execs it.

**Architecture:** One line in `pyproject.toml`'s `[project].dependencies`, one regenerated
`uv.lock`. Nothing else changes: the venv that gains `supervisord` is already built by
`docker/DispatcharrBase`'s existing `uv sync --python 3.13 --no-cache --no-install-project --no-dev
--locked` (`docker/DispatcharrBase:53`), so no Dockerfile, entrypoint or ini edit belongs in this
PR — that is PR 3's job.

**Tech Stack:** `uv` 0.12.5 (the exact version `lint.yml`'s `uv lock --check` runs), Python 3.13,
PyPI `supervisor` 4.3.0.

**Spec:** `docs/superpowers/specs/2026-09-04-phase1-process-split-design.md` § The eight pull
requests › PR 1, and D2 under § Decisions.

**Branch:** `migration/phase1-supervisor-dep` (worktree `.worktrees/phase1-pr1`), off `main`.

## Global Constraints

- `pyproject.toml`'s dependency array pins with `==` for 11 of its entries (exact-pin style; 32
  entries total before this PR, verified with `awk '/dependencies = \[/,/^\]/' pyproject.toml |
  grep -c '^\s*"'`); a version-changing dependency uses `==`, never a range —
  `supervisor==4.3.0` follows that half of the convention (D2).
- **No entrypoint, ini, or `docker/DispatcharrBase` change in this PR.** The dependency lands
  alone so a PR that both adds it and execs it does not fail its own image build (D2, confirmed
  live: `docker/DispatcharrBase` builds the venv solely from `uv sync --locked --no-dev` against
  `pyproject.toml`/`uv.lock`, and `base-image.yml` only rebuilds the shared `:base` tag on push to
  `main`).
- `uv.lock` is regenerated by `uv`, never hand-edited.
- Regenerate with the exact `uv` version and image `lint.yml`'s freshness check runs
  (`ghcr.io/astral-sh/uv:0.12.5-python3.13-trixie-slim@sha256:d1e005e6f5aac724b7554db95f1c128a77d8d35b59ebe70e188852b4bdad3a3d`),
  not the host's `uv 0.12.7` — a patch-version mismatch can change `uv.lock`'s resolution or
  `revision =` field and fail `uv lock --check` in CI even though the dependency itself is correct.
- **`git add` and `git commit` in separate Bash calls.** The `PreToolUse` hook matches on Bash
  command *text* and fires before every `git commit*` call, so a single call doing both stage and
  commit runs the gate before anything is actually staged and gets blocked — this is general, not
  specific to this PR's message content. Because the match is textual, a `-m`/heredoc commit
  message that itself contains the words "git add"/"git commit" trips the same gate; write every
  commit message to a file with the Write tool and commit with `git commit -F <file>` so the
  message text never appears in the Bash command string the hook scans.
- **`gh` calls always pass `--repo D10Scot/Dispatcharr`** — plain `gh` resolves to the upstream
  public tracker.
- Branch must be named `migration/phase1-supervisor-dep` (a `migration/**` prefix) so
  `lifecycle-tests.yml`'s `suites` job and the full E2E project matrix run on this PR
  (`lifecycle-tests.yml:119-124`, `:231`); an ordinary branch name would get the gated,
  changed-paths-only matrix instead and this PR's done criteria would not be provable.

The edit/commit hooks resolve the project directory from the harness, so in a worktree they do not
run tests automatically. Run them yourself:

   `CLAUDE_HOOK_REPO_ROOT=<worktree> DISPATCHARR_TEST_CONTAINER=dispatcharr-testrunner-pr1 <worktree>/.claude/hooks/pre-commit-tests.sh --git-hook`
