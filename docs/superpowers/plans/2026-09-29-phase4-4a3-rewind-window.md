# Plan: Phase 4a-3, the live rewind window, linger and lingering reclaim

> **For agentic workers:** implement this plan task by task with subagents, per CLAUDE.md § Delegation for phase work. The Go, Python and frontend code is specified by its contracts below (types, signatures, lock order, flows, test names and their oracles), not by a diff: the implementer writes it. Every documentation and configuration edit is Appendix A, a byte-exact `git diff` that the implementer applies and does not rewrite; its only non-literal parts are the `⟨…⟩` slots, each of which names exactly what fills it.

**Goal.** An HLS channel keeps its last `rewind_window_minutes` (60) on disk from its first HLS viewer, shared by every viewer and listed in its media playlists as a sliding window, so AVPlayer can pause, rewind and scrub back to live. When its last HLS viewer leaves, the channel lingers for `rewind_linger_seconds` (300) so a zap back keeps the rewind; a lingering channel is reclaimable by a blocked tune at once, or, when its viewer stopped without a leave while watching behind live, after `rewind_behind_live_grace_seconds` (10). The window is lost on restart and on drain, bounded process-wide by `rewind_disk_cap_gb` (16), and a disk failure degrades the window, never the live output. This is the last PR of Phase 4a. ## Global constraints

1. **Standard library only**, and no Redis or Postgres by any route (`scripts/check_go_stdlib_only.sh relay`). The rewind store is `os`, `io/fs`, `path/filepath`, `crypto/rand`, `crypto/sha256`, `encoding/hex`, `sync`, `sync/atomic` and `time`.
2. **No disk I/O on the segmenter's goroutine or under any lock.** `Store.publish` runs on the segmenter's goroutine under `s.mu` (`relay/hls/store.go:112-141`); it may only queue a segment and send a non-blocking wake-up. Every `mkdir`, write, rename, read and unlink runs on the rewind writer's goroutine or on a request's own goroutine with no lock held. A test holds this (BC5).
3. **The lock order is unchanged: `m.mu` → `c.mu` → `st.mu`** (spec § Locks), plus the channel's `outMu`, which still never nests with `c.mu` (`relay/channel/output.go:121-125`). The linger's state is an `atomic.Pointer`, written only under `outMu` and read anywhere without a lock, so reading it under `m.mu` or `c.mu` adds no edge. The store's `s.mu` and the rewind store's `r.mu` never nest in either direction.
4. **A segment being served is never deleted under its reader** (§ The design, Reads). A test holds this deterministically (BC6).
5. **Every error a log or format call carries goes through `redact.Error`**, or carries `// credential-logging: ok - <reason>`. No new log line names a URL or a token. The rewind store's paths name a channel id, a run number, a generation, a rendition and a sequence, never a credential.
6. **Zero lint findings under three GOOS** (`golangci-lint run ./...` natively, `GOOS=linux`, `GOOS=darwin`, v2.13.2), `go vet` and `go test -race ./...` green.
7. **Deterministic waits.** The linger timer is injected (`ManagerConfig.AfterFunc`); the grace and the silence run on the session table's injected clock; the depth sweep and its retention on the store's; a test that waits for the writer waits on an event (`Rewind.Sync` for a completed batch, `Store.WaitDurable` for a written segment, `Store.WaitDegraded` for a degradation), never on a count reaching `baseline + N`. No test sleeps out a linger, a depth or a grace.
8. **The test-modification rule.** An existing test changes only where the behaviour it pins is the thing this PR changes, and every such change, and every test-support edit that changes no assertion, is listed in § Tests changed with its before and after.
9. **Parity rows ⟨E⟩-⟨H⟩ land pinned** in the `phase 4` block, rows 43, 45 and 46 are amended in place, and `HIGHEST_ROW_ID` rises to the last new id in the same diff (Appendix A; Task 10).
10. **The spec amendments ride in this plan PR**, not the implementation PR. The implementation PR edits no spec text.
11. **Python Gate 2 does not move.** `apps/proxy/relay_serializers.py` is one of its nine modules; its new lines are field declarations, covered at import, and `scripts/coverage_live_path_isolated.sh` shows `missing` 33 before push.

## Decisions the spec leaves open

Each is this plan's ruling, open to challenge; those that changed spec text were put to the orchestrator and are now rulings R82-R87 (§ Rulings on the plan's questions), which the spec amendments cite.

1. **The rewind store lives in `relay/hls`**, not a new package: `rewind.go` (the process-wide store and its writer goroutine) and the window half of `store.go`. A new package would be a first link under R27, with its own per-package census, for no seam anybody needs.
2. **One process-wide writer goroutine**, owned by `hls.Rewind`, does every disk operation for every window: writes, renames, unlinks, the cap, the removal of a stopped pipeline's directory. Accounting against the cap is then single-threaded. It serialises all channels' writes, which at D8's top rate is about 1 MB/s per channel; a slow `RemoveAll` of a stopped pipeline delays other windows' writes, which their queues absorb (`StoreSegments` segments, 42 s at a target of 2).
3. **The window's bytes stay in memory until written.** A segment is marked *pending* when `publish` queues it and keeps its data even after it leaves the newest 21, until the writer has written it, so a slow disk loses nothing. The window counts its pending segments (`w.pending`: queued and not yet written, whether or not the writer has taken them from the queue; decremented when one is written or the window degrades), and a `publish` that finds `w.pending` already at `StoreSegments` degrades the window (Decision 8), which bounds the extra memory at one store's worth and makes the `StoreSegments + 1`-th unwritten segment the deterministic trigger.
4. **The playlist keeps RFC 8216 § 6.2.2 for what only memory holds.** A segment is *durable* when it is on disk or pending. The media playlist lists `s.segs[k:]`, where `k` is the smallest index from which every segment is durable or among the newest `LiveEdge`. (`s.segs` is always contiguous: `trimLocked` retires a non-durable segment below the newest 21 together with everything older. `k` exists so that a non-durable segment leaves the playlist when it leaves the newest 10, 11 publications before it leaves memory, as R44's live edge does.) With the window off nothing is ever durable, so `k = len − LiveEdge`, exactly 4a-1b's live edge; with a healthy window `k = 0`. The rendered bytes are cached per rendition until the store next changes, and every mutation counts as a change (§ The design, `notifyLocked`) (measured: 0.54 ms and 148 KB for 1,800 entries).
5. **Depth removes from the playlist by PDT; the unlink waits a retention.** A segment more than `WindowDepth` older than the newest (by PDT), and outside the newest 21, leaves the playlist into a *retired* list, stays fetchable by URL for `UnlistedRetention` = `(StoreSegments − LiveEdge)` × the store's target (22 s at 2), and is then unlinked by the writer (R83).
6. **The cap's eviction order**: retired segments of any window, oldest first; then the oldest listed segment of a lingering window (by PDT); then the oldest listed segment of any window. Only segments outside a window's newest 21 are ever evicted, and only `onDisk` ones: a `pending` segment is skipped (it has no file yet) and becomes evictable once written. Since a listed victim is always its window's head, a window whose head is pending contributes no listed victim until that head is written. A cap eviction unlinks at once. If nothing is evictable the writer logs at WARNING that the cap cannot be met, once until the cap has been met again, and tries again at the next batch.
7. **Reads pin.** A read of an on-disk segment takes, under `s.mu`, a pin on the segment and on its window, releases the lock, reads the file, and unpins. An eviction or retirement of a pinned segment marks it *doomed* and its unlink waits for the last unpin; a stopped pipeline's directory is removed only when its window has no pin, and the batch that decides to remove it marks the window *removing* in the same critical section, after which `SegmentAt` refuses every disk read of that window (not found), so no read can start between that decision and the `RemoveAll`. Unlinking an open file is safe on Linux and macOS, but the pin covers the whole read, so the property does not depend on it.
8. **Degradation is per pipeline run** (the spec says "channel's run"; a later pipeline on the same channel tries the disk again). A `MkdirAll`, `WriteFile` or `Rename` error, or a full queue, degrades the window: it stops queueing, its pending segments become non-durable, the playlist shrinks to the live edge as they age out (Decision 4), `rewind_degraded` is set, and one WARNING is logged per window. The pipeline, its sessions and the channel are unaffected.
9. **The boot directory is made on first use and retried at every window open.** `NewRewind` never fails and never blocks on the disk; a window opened while the boot directory cannot be made starts degraded. The start-up sweep of every other boot directory is `go rewind.CleanStale()`, off the path to `ListenAndServe`.
10. **Layout:** `<root>/<boot-id>/<channel>/<run>/<gen>/<rendition>/<seq>.m4s` and `…/<gen>/<rendition>/init.mp4`; `<run>` a per-`Rewind` counter; `<channel>` the id when it matches `^[A-Za-z0-9_-]{1,64}$`, else `x` + the first 16 hex characters of its SHA-256. Temporary files are `<name>.tmp`, renamed into place (R85).
11. **The linger is the channel's, the grace is the session table's.** The channel holds at most one linger (`c.linger atomic.Pointer[lingerState]`: key, pipeline, since, timer), started by `hlsRelease` at zero sessions and ended by a new session, a resume, its timer, a failure or the channel's stop. The grace needs no linger state at all: an idle-departed behind-live session stays in the table as DEPARTED (4a-1b already keeps it for its resume window), and the judge reads it. This is what keeps the grace in one clock (the table's) and makes it apply equally to a lingering channel and to one in a `channel_shutdown_delay` countdown (R82).
12. **When a pipeline lingers:** at its last session's release, when `Tuning.RewindWindow > 0`, `Tuning.RewindLinger > 0`, the pipeline is ready (`Pipeline.IsReady`) and has not ended, the channel's outputs are not stopped, and no other pipeline of the channel lingers. So a leave, an admin client stop or stream-limit termination (R84) and an idle departure all linger, while an entry that never served its multivariant (its pipeline not yet ready) and a pipeline whose sessions went STOPPED (their releases are discarded, `relay/session/table.go:346-360`) never do. No new parameter crosses the release func: its signature is unchanged.
13. **The linger holds the channel through `Manager.stopWhenIdle`**, which returns without arming anything while `c.lingerHeld()`: `release` calls it directly (`relay/channel/manager.go:479-484`), so the check must be there, or a `channel_shutdown_delay` countdown armed at the last client's release would fire during the linger or shortly after it and cut the delay short. `stopIfStillIdle` re-checks under `m.mu`. `StopIfIdle` gains no check of its own: it reaches `stopWhenIdle`, whose return is the one mechanism for it, so a second guard there would be masked and unpinnable. So the countdown starts only when the client count and the hold are both zero (spec § The ADR 0006 amendment), and it goes through `ManagerConfig.AfterFunc` too, so a test can see it. The linger's end calls the channel's `onIdle` (the manager's `StopIfIdle`) off every lock, on the timer's own goroutine.
14. **Behind live is decided per served media segment**, when it is served: `Store.SegmentAt` returns how far the segment's PDT is behind the newest's, and the handler records `behind > BehindLiveAfter(TD)` (5 × TD) on the session with `Table.NoteSegment`. The latest served segment decides; a playlist, an init or a 404 moves nothing.
15. **The settings' bounds**: `rewind_window_minutes` 0-120, `rewind_linger_seconds` 0-3600, `rewind_behind_live_grace_seconds` 0-300, `rewind_disk_cap_gb` 1-10000, integers, `required=False` with the D17 defaults, the idiom `channel_client_wait_period` already uses (`core/serializers.py:107-108`). The relay serializer declares all four `FloatField`, as it declares the other stored keys it renders verbatim.
16. **The disk cap is the most recent initial tune's value** (`startTune` sets it from `tuningFrom`'s result). A failover answer does not re-read settings. Before the first tune the cap is unlimited, and no window can open before a tune.
17. **The Go fake control plane carries `rewind_linger_seconds: 0`**, not Django's 300 (`relay/internal/relaytest/controlplane.go:26-51`). Every pre-4a-3 rig test pins a last leave that **stops** its channel, and 4a-1c's case-(a) oracle (`TestABlockedTuneWaitsForAReleaseInFlight`) needs A in the releasing set, not lingering; with 300 there, that test would pass through case (b) instead and go hollow. The linger tests opt in with their own settings. Its `rewind_window_minutes` is 60, and the rig builds no `Rewind` unless a test asks (`withRewind`), so every existing playlist assertion is on the live edge as before.
18. **Payload fields.** `lingering_since` (a Unix float, while the linger lasts), `rewind_window_seconds` (the rendered video playlist's summed `EXTINF`, while an HLS pipeline is registered) and `rewind_degraded` (present only when true), on both `/proxy/relay/channels` and `/proxy/relay/channels/<id>`, declared optional in `apps/proxy/relay_serializers.py`.
19. **The capability document** reports `rewind_window: {available: minutes > 0, depth_seconds: minutes × 60}` from `CoreSettings.get_proxy_settings()`.
20. **E2E hygiene.** Every E2E test that opens an HLS session stops the channels it tuned in its `finally` through a new `stopChannels(api, …uuids)` helper, so a 300 s linger never runs an encode behind the next test on a CI runner already near real time for 1080i (R29; R87).

## Rulings on the plan's questions (R82-R87)

The round-0 draft asked six questions; the orchestrator ruled each as recommended (2026-09-29). Each is stated here as ruled.

- **R82, where the behind-live grace runs from.** The spec said a lingering window is reclaimable at "lingering-start + grace", the linger starting at the idle departure (12 s after the last request at TD 2). But 4a-1c's D16 already reclaims a session silent for more than 2 × TD (R24), so a behind-live viewer that stops without a leave would be reclaimable at 4 s and the grace would protect nothing (the spec's own E2E, "B gets 503 until the grace ends", would fail). Ruled: the grace runs from the session's silence point, `lastEnd + 2 × TD + grace` (14 s at the defaults), for any idle-departed behind-live session of the channel and for any zero-client channel, including one in a `channel_shutdown_delay` countdown; D15's summary line is read through § Linger as amended. R25 is untouched: a leave removes its session, so it has no grace.
- **R83, RFC 8216 § 6.2.2 at the window's head.** Read literally, a segment the depth sweep removes must stay available for a 60-minute playlist's duration, doubling the disk. Ruled: `(StoreSegments − LiveEdge)` × TD, 22 s at TD 2, R44's live-edge arithmetic. A cap eviction unlinks at once (§ Risks).
- **R84, an admin client stop or a stream-limit termination** lingers, with grace 0 (its session is removed, as a leave's is).
- **R85, the layout** gains a per-pipeline `<run>` directory (Decision 10).
- **R86, the E2E depth scenario** checks the default depth (sequence 0 still listed after more than 21 segments, segment 0 served from disk); the sweep and its retention are pinned in Go with an injected clock.
- **R87, E2E cleanup.** Every existing HLS E2E stops its channels in `finally` (Decision 20), a support edit listed in § Tests changed.

### `relay/hls`: the rewind store (`rewind.go`, new)

```go
// DefaultRewindRoot is where the rewind windows live (spec D14);
// docker/init/03-init-dispatcharr.sh creates it.
const DefaultRewindRoot = "/data/cache/rewind"

// FS is the disk as the rewind store uses it: OSFS in production, a
// fault-injecting one in tests (spec: "Tests inject the writer").
type FS interface {
	MkdirAll(dir string) error                 // 0o755
	WriteFile(name string, data []byte) error  // create or truncate, 0o644
	Rename(from, to string) error
	ReadFile(name string) ([]byte, error)
	Remove(name string) error
	RemoveAll(dir string) error
	ReadDir(dir string) ([]string, error)      // entry names
}

// OSFS is FS over package os.
type OSFS struct{}

type RewindConfig struct {
```

Unexported: `r.kick chan struct{}` (capacity 1; every sender uses a non-blocking send), `r.mu` guarding the window set and the cap, `r.total atomic.Int64`, `r.nextRun atomic.Uint64`, `r.bootReady bool` (writer-owned), `open(channelID string, depth time.Duration, store *Store) *window`, `loop()`, `work()`, `enforceCap()`, `degrade(w *window, err error, why string)`.

**The writer's batch (`work`)**, woken by `kick` and by nothing else. `r.started` and `r.done` count batches (under `r.mu`), and `r.batchDone` is a channel closed and replaced at each batch's end:

1. Snapshot the window set under `r.mu`, then release it.
2. For each window, under its store's `s.mu`: take its pending segments (in order, with the init bytes of each `(gen, rendition)` not yet written from `s.inits`), its unlink list, its retired segments whose retention has passed and which have no pin (removing them from the retired list; one still `pending` is also dropped from the queue with `w.pending--`, so the writer never writes a file it is about to unlink), and whether it is closed with no pin; if so, mark it `removing` in this same critical section. Release `s.mu`.
3. A `removing` window: `RemoveAll(runDir)`, subtract its bytes, forget it. Next window. (No read can start after the mark: `SegmentAt` refuses a `removing` or `closed` window's disk reads.)
4. If `!r.bootReady`: `MkdirAll(BootDir)`; on failure degrade the window and go on.
5. For each pending segment, for each rendition: `MkdirAll` of its `<gen>/<rendition>` directory (once per window), `init.mp4` if that `(gen, rendition)` has none yet (temporary name, then rename; nothing reads it, since inits are served from `s.inits`, and it is kept so that a run directory is self-describing for the future TS reader, R10), then `<seq>.m4s` (temporary name, then rename). The first error degrades the window and ends its batch. On success, under `s.mu`: a segment no longer in `s.segs` or `retired` (evicted or retired and unlinked meanwhile) is not marked on disk, its bytes are not counted, and its new files are queued for unlink at once, so no orphan is ever counted against the cap; otherwise, and only if the window has not degraded meanwhile (a degraded window's results are ignored: its `w.pending` is already 0 and its segments stay non-durable; the orphaned files go with the run directory): `pending=false`, `w.pending--`, `onDisk=true`, the window's bytes and `r.total` grow, and `trimLocked` runs (it releases the data of a written segment that has left the newest 21), then `notifyLocked`.
6. `Remove` each unlink path; an error other than not-exist is logged at DEBUG.
7. `enforceCap()`: while `r.total > cap`, pick a victim (Decision 6: `onDisk` only, never a `pending` one; a window's listed victim is always its head, since eviction only ever removes from the head, so a window whose head is `pending` contributes no listed victim this batch, while its retired `onDisk` segments stay eligible under tier 1), each window peeked under its own `s.mu` one at a time, never two at once. Under that `s.mu`, decide and edit the lists only: a retired victim leaves the retired list; a listed one leaves `s.segs` from the head, counting a discontinuity into `discontinuitiesGone`; a pinned one is marked `doomed` instead of unlinked; subtract its bytes; `notifyLocked`. Then release `s.mu`, and only then `Remove` the unpinned victim's files, as Global constraint 2 requires.
8. Under `r.mu`, `r.done++` and close `r.batchDone`: the batch's end, after its writes, unlinks and evictions. `Sync` waits on it.

`degrade` (under `s.mu`): `degraded = true`, every pending segment becomes non-durable and `w.pending` is 0, the queue is dropped, `trimLocked`, `notifyLocked`, one WARNING per window: `"the rewind window stopped persisting; the live edge is unaffected"` with the channel, the run and `redact.Error(err)` or the reason ("the writer queue is full").

## Risks

- **Rapid zapping leaves a lingering encode per channel zapped through**, for `rewind_linger_seconds` each, on an unlimited provider (a slot-limited one reclaims them). The owner's Q1 CPU measurement bounds how many a host can carry; a follow-up could shorten the linger of a window that never grew past its live edge.
- **Cap eviction is immediate**, so a player at the very head of a window under cap pressure can see a 404 for a segment its last playlist listed.
- **Disk wear**: the spec's § Risks bullet stands; the writer's temporary-then-rename doubles no data (the rename is metadata).
- **PDT drift** moves the depth sweep with it (the spec's § Risks bullet).
- **A Redirect-profile channel lingers too.** Played over HLS it is served as Proxy (D13), and after its last HLS session it keeps running for the linger, so a TS tune in that time attaches to the running channel rather than getting its 302 (parity row 42's "while it is not running" covers it: the channel is running).
- **A relay container whose `/data/cache/rewind` is never made writable** runs degraded for its life, logged once per window.
