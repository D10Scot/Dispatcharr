## PR 1 — #556: a same-name re-upload deletes the file just written

### Root cause

`M3UAccountViewSet.update()` (`apps/m3u/api_views.py:149-246`):

- `:163` computes the new path from the uploaded basename alone:
  `file_path = safe_upload_path(file.name, "/data/uploads/m3us")`. `safe_upload_path`
  (`core/utils.py:653-664`) returns the **resolved** `base/basename`.
- `:167-170` writes the upload to that path.
- `:188-189` then removes the account's previous file, unconditionally:
  `if instance.file_path and os.path.exists(instance.file_path): os.remove(instance.file_path)`.
- `:192` `super().update()` saves `file_path` (the new path) on the account.

When the upload's basename equals the current file's, both paths are the same file, so `:189` deletes
what `:168-170` just wrote, and `:192` saves the account pointing at nothing. The next refresh of that
account cannot read its playlist. `partial_update()` (`:249-264`) reaches the same code through
`super().partial_update()` → `self.update(partial=True)`. The view is admin-only
(`permission_classes_by_action["update"]`), so there is no security impact.

### Reproduced at seed

The new module (Appendix 556-B) against unmodified `a1e9da65`, private container `plan-554-556`:

```

AssertionError: False is not true : the upload was written to /tmp/m3u-reupload-uj53mk36/playlist.m3u and then deleted by the old-file cleanup, which removed the same path
FAIL: test_reupload_under_the_same_name_keeps_the_new_file
AssertionError: False is not true : the upload was written to /tmp/m3u-reupload-mm565wz7/playlist.m3u and then deleted by the old-file cleanup, which removed the same path
Ran 3 tests in 0.077s
FAILED (failures=2)
```

The third test (a re-upload under a new name removes the previous file) passes at seed: it pins the
cleanup the fix must keep.

### Fix

Remove the previous file only when it is not the file just written, comparing resolved paths
(Appendix 556-A, one condition added at `:188`):

```python
            if (
                instance.file_path
                and os.path.exists(instance.file_path)
                and os.path.realpath(instance.file_path) != os.path.realpath(file_path)
            ):
                os.remove(instance.file_path)
```

Why `realpath` and not `!=`: `safe_upload_path` resolves symlinks, and `file_path` is stored as a
`CharField` (`apps/m3u/models.py:40`), so a stored value written by an older release, by an admin
through the API, or through a symlinked `/data` can spell the same file differently. A string compare
would still delete the new file in that case; `test_reupload_through_a_symlinked_spelling_...` pins it
(BC-556-2).

Why not "remove before writing" (the issue's other option): it would delete the old file before the
new one is known to have been written, so a failed write would leave the account with neither. The
condition keeps today's order and today's behaviour for every re-upload under a new name.

Not in scope, and deliberately not changed (§ Follow-ups): making stored names unique per account (the
`create()` collision, `:98-105`, where two accounts that upload the same basename share one file), and
the removal running before `super().update()` validates (a 400 from the serializer still leaves the old
file deleted and the account pointing at it). Both are behaviour changes the issue asks to be stated
explicitly; #556 needs neither.

### Test design

`PATCH /api/m3u/accounts/<id>/` with a multipart upload through `APIClient` as an admin

## PR 2 — #554, #207, #289: `_redact_url` fails open and misplaces the host

**Scope (owner ruling R106).** A fable verifier found that CodeQL alerts 95 and 96 (#207, #289) are
true positives from this same helper (evidence: the orchestrator's `codeql/verify.md`, § 3 and N1/N2).
So this PR makes `_redact_url` **fail closed** as well as fixing the `@` handling, and it closes all
three issues. Hardening the `get_transformed_credentials` shortcut that can produce a scheme-less URL
(`apps/m3u/tasks.py:3143-3150`) is out of scope (§ Follow-ups).

### Root cause

`_redact_url` (`apps/timeshift/views.py:3738-3746`) is the local helper that reduces a provider URL to
`scheme://host/...` before it is logged. It has two defects:

```python
    if not url or "://" not in url:            # :3740
        return url                             # :3741  FAIL-OPEN: no "://" -> returned whole
    scheme, rest = url.split("://", 1)        # :3742
    if "@" in rest:                            # :3743
        rest = rest.split("@", 1)[1]           # :3744  FIRST "@" anywhere after the scheme
    host = rest.split("/", 1)[0]               # :3745  stops at "/" only
```

1. **Fail-open (alerts 95/96, #207, #289).** A string with no `://` comes back unchanged. That is exactly
   the input `requests` refuses before connecting (`MissingSchema`, or `InvalidSchema` for a string
   whose first segment reads as a scheme; both are `RequestException`). `_open_upstream`
   (`:3203-3225`) raises it into `except requests.exceptions.RequestException` (`:3342`), and the URL is
   logged whole at WARNING (`:3344-3348`, cached-final branch) or ERROR (`:3351-3355`). The URL is
   `f"{creds.server_url.rstrip('/')}/..."` (`apps/timeshift/helpers.py:422`, `:434`), and the XC
   password follows in its query (format A) or path (format B). A scheme-less `server_url` cannot come
   through the serializer (`validate_flexible_url`), but it can come through an M3U profile replace
   pattern that drops the scheme (`get_transformed_credentials`, `apps/m3u/tasks.py:3143-3150`, returns
   what precedes the credential suffix unvalidated) or a row written outside the serializer.
2. **Wrong host (#554).** `rest` is the whole remainder of the URL, not its authority, and the split
   takes its **first** `@`. So a literal `@` in a userinfo password, an `@` anywhere in the path or
   query (a provider CDN token in `response.url`, logged at `:3435`), a query with no path, or a netloc
   holding a fullwidth `@` each puts part of a credential where the host should be.

The same helper also feeds the catch-up channel's stats metadata (`:3121`, `ChannelMetadataField.URL`).
Each log call carries a `credential-logging: ignore - already redacted by the local _redact_url()
helper` marker, so `scripts/check_credential_logging.py` cannot see a leak through it. At seed that
marker was false for the fail-open input; after this PR it is true, so its wording stays and only its
stale line numbers go.

The URLs Dispatcharr builds from a well-formed `server_url` never hit either defect:
`build_timeshift_url_format_a`/`_b` (`apps/timeshift/helpers.py:418-440`) encode the XC username and
password with `quote(..., safe='')`, which turns `@` into `%40`.

### Fix: fail closed, last `@` of urlsplit's authority, mask what is ambiguous

Appendix 554-A rewrites the helper's body:

```python
    if not url:
        return url
    if not isinstance(url, str):
        return REDACTED
    try:
        parts = urlsplit(url)
    except ValueError:
        return REDACTED
    if not parts.scheme or not parts.netloc:
        return REDACTED
    if "@" in parts.path or "@" in parts.query or "@" in parts.fragment:
        return REDACTED
    host = parts.netloc.rpartition("@")[2]
    try:
        parts.port  # raises ValueError on a non-numeric or out-of-range port
    except ValueError:
        return REDACTED
    if not host or not host.isprintable() or any(c in host for c in "%\\; \t"):
        return REDACTED
    return f"{parts.scheme}://{host}/..."
```

- **Fails closed.** Anything without both a scheme and a host (`urlsplit`'s `scheme` and `netloc`) is
  masked whole with `REDACTED` (`"***"`, `dispatcharr/utils.py:59`), the mask `redact_url` already
  uses. So is anything `urlsplit` refuses (a malformed IPv6 literal, or a netloc that NFKC-normalises to
  a delimiter), and anything that is not a `str`. The helper never raises. Any falsy value (`None`, `""`,
  and equally `0` or `b""`) carries nothing and comes back as given; no caller passes a falsy
  non-`str`. `:3121` already guards `None`, and the existing `assertIsNone(views._redact_url(None))`
  keeps its pin.
- **The catch-up stats metadata changes too.** `:3121` stores `_redact_url(primary_url)` as
  `ChannelMetadataField.URL`, so for a scheme-less (or otherwise unplaceable) `primary_url` that
  metadata now holds `***` where it held the raw string, password included. It is visible wherever a
  catch-up channel's stats are shown. A well-formed `primary_url` stores `scheme://host/...` as before.
- **The authority is urlsplit's netloc**, which ends at the first `/`, `?` or `#`, so a query with no path
  is no longer part of the "host".
- **The host is what follows the netloc's last `@`**: the rule `urlsplit` (`.hostname`),
  `urllib3.parse_url` (what requests dials) and `dispatcharr.utils._redact_netloc`
  (`dispatcharr/utils.py:124-129`) all apply. The port is kept.
- **An `@` after the authority masks the URL whole.** With a `/`, `?` or `#` unencoded in a password,
  urlsplit ends the netloc inside the userinfo: `http://usr0:12/tail9@example.invalid/x` has netloc
  `usr0:12`, which reads as host `usr0`, port `12`. The seed helper happens to get that case right
  (first `@` of the remainder), so a rule built on urlsplit alone would regress it. The `@` after the
  netloc is the only sign, and `http://usr0:12/tail9@host/` cannot be told apart from
  `http://host:12/a@b/`, so both are masked. This also covers R106's `?token=abc@def` case: it masks
  rather than logging `http://cdn.example.invalid/...`. A legitimate URL with an `@` in its path or
  query loses its host from the log line, and nothing else changes.
- **What is left must look like a host** (ruling R112, review round 2 F4). With no `@` in the netloc,
  `rpartition("@")[2]` is the whole netloc. So an encoded `@` (`alice:s3cret%40myhost`), a backslash
  typed for a delimiter (`alice:s3cret\myhost`), or a `;` after the host (`myhost;s3cret`) would print
  userinfo as the "host". Two checks follow the `rpartition`:
  - `parts.port` masks a port that is not a number. Python 3.13's `port` takes everything after the
    **first** `:` of the unbracketed hostinfo (after the last `@`) and needs ASCII digits in 0-65535.
    So a non-numeric port, a second `:` (`a:s3cret:80`), a sign, a space, non-ASCII digits and an
    out-of-range port all raise, and `alice:s3cret` (no `@`) is masked (probed in the container). **This
    answers R112's question: a `:` in a non-bracketed host followed by anything other than a valid port
    is covered by the `parts.port` check alone.** The one shape it cannot catch is `alice:1234`, a
    username with an all-digit password and no `@host`. It is indistinguishable from host `alice`,
    port `1234`, and is printed as such; no rule can tell them apart.
  - The character check masks an empty host (`http://u:p@/x`), an unprintable one, and one holding `%`,
    `\`, `;`, a space or a TAB. It is the only check that catches a token-only userinfo with no `:`
    (`s3cret%40myhost`, `s3cret\myhost`) and `myhost;s3cret`; BC-554-9 shows it. A zone-scoped IPv6
    literal (`[fe80::1%25eth0]`) is masked by the `%` rule, which the R110 trade-off already accepts.
- **Output shape** stays `scheme://host/...`. The scheme is now urlsplit's, which is lowercased.
- **The five stale marker comments** (`(:3621)` at `:3345`, `:3352`, `:3364`, `:3433` and `(:3580)` at
  `:3400`; the helper is at `:3738`) say `(below)` instead of a line number that drifts again. The
  reason text is kept. The markers are accurate once the helper fails closed, and the checker accepts
  each one (`check_credential_logging.py` exits 0 on both files).

**Why not delegate to `dispatcharr.utils.redact_url`.** It does not do this. It keeps the path and
query and masks only the shapes it knows, and it returns a relative or scheme-less string as given
when nothing in it matches those shapes. This helper's contract is `scheme://host/...`, which the stats
metadata at `:3121` also relies on. It also has its own version of the slash case (§ Other redaction
helpers). The fix reuses its host rule, not the function.

**Why not the issue's `.hostname` + `.port`.** It leaks the username and the head of the password in
the slash case (BC-554-4: `http://usr0:12/...`).

## PR 3 — #555: strict mode admits `100.64.0.0/10`

### Root cause

`validate_outbound_http_url` (`core/http_security.py:14-146`) classifies each resolved address by
category (`:124-143`): loopback (refused unless `allow_loopback`), unspecified, multicast and link-local
(always refused), private (refused unless `allow_private`), reserved (always refused). It never asks
`is_global`. An address outside every category passes in strict mode (`allow_private=False`).

Enumerated under Python 3.13.15 (the container's; `.python-version` is `3.13`), one address per IPv4
`/16`, plus every `192.0.0.x` and a set of IPv6 forms: the addresses that are **not** global and in
**none** of the six categories are exactly `100.64.0.0/10` (RFC 6598 shared address space: carrier-grade
NAT, Tailscale's tailnet range) and its IPv4-mapped form `::ffff:100.64.0.0/106`. Every other non-global
range the sweep found is already private or reserved (`192.0.0.0/24` apart from `.9`/`.10`,
`192.0.2.0/24`, `198.18.0.0/15`, `240.0.0.0/4`, `64:ff9b:1::/48`, `2001::/23`, `2002::/16`, …), and the
NAT64 prefix `64:ff9b::/96` is reserved, so it is refused even when it embeds a global address.

Strict-mode callers are the plugin fetches only: `_validate_fetch_url` and `_fetch`
(`apps/plugins/api_views.py:84-100`), reached from `_fetch_manifest` (`:787-791`; called at `:826`,
`:871`, `:996` and by the Celery task `apps/plugins/tasks.py:20`) and from the install path
(`:1151`, `:1161`, `:1277`, `:1281`). The views are admin-only POSTs. The one lenient caller,
`core/image_proxy.py:116` (`allow_private=True`), is unaffected by design (below).
