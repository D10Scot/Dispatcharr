## PR 1 — #556: a same-name re-upload deletes the file just written

### Root cause

`M3UAccountViewSet.update()` (`apps/m3u/api_views.py:149-246`):

- `:163` computes the new path from the uploaded basename alone:
  `file_path = safe_upload_path(file.name, "/data/uploads/m3us")`. `safe_upload_path`
  (`core/utils.py:653-664`) returns the **resolved** `base/basename`.
- `:167-170` writes the upload to that path.
- `:188-189` then removes the account's previous file, unconditionally:
  `if instance.file_path and os.path.exists(instance.file_path): os.remove(instance.file_path)`.
- `:192` `super().update()` saves `file_path` (the new path) on the account.

When the upload's basename equals the current file's, both paths are the same file, so `:189` deletes
what `:168-170` just wrote, and `:192` saves the account pointing at nothing. The next refresh of that
account cannot read its playlist. `partial_update()` (`:249-264`) reaches the same code through
`super().partial_update()` → `self.update(partial=True)`. The view is admin-only
(`permission_classes_by_action["update"]`), so there is no security impact.

### Reproduced at seed

The new module (Appendix 556-B) against unmodified `a1e9da65`, private container `plan-554-556`:

```

AssertionError: False is not true : the upload was written to /tmp/m3u-reupload-uj53mk36/playlist.m3u and then deleted by the old-file cleanup, which removed the same path
FAIL: test_reupload_under_the_same_name_keeps_the_new_file
AssertionError: False is not true : the upload was written to /tmp/m3u-reupload-mm565wz7/playlist.m3u and then deleted by the old-file cleanup, which removed the same path
Ran 3 tests in 0.077s
FAILED (failures=2)
```

The third test (a re-upload under a new name removes the previous file) passes at seed: it pins the
cleanup the fix must keep.

### Fix

Remove the previous file only when it is not the file just written, comparing resolved paths
(Appendix 556-A, one condition added at `:188`):

```python
            if (
                instance.file_path
                and os.path.exists(instance.file_path)
                and os.path.realpath(instance.file_path) != os.path.realpath(file_path)
            ):
                os.remove(instance.file_path)
```

Why `realpath` and not `!=`: `safe_upload_path` resolves symlinks, and `file_path` is stored as a
`CharField` (`apps/m3u/models.py:40`), so a stored value written by an older release, by an admin
through the API, or through a symlinked `/data` can spell the same file differently. A string compare
would still delete the new file in that case; `test_reupload_through_a_symlinked_spelling_...` pins it
(BC-556-2).

Why not "remove before writing" (the issue's other option): it would delete the old file before the
new one is known to have been written, so a failed write would leave the account with neither. The
condition keeps today's order and today's behaviour for every re-upload under a new name.

Not in scope, and deliberately not changed (§ Follow-ups): making stored names unique per account (the
`create()` collision, `:98-105`, where two accounts that upload the same basename share one file), and
the removal running before `super().update()` validates (a 400 from the serializer still leaves the old
file deleted and the account pointing at it). Both are behaviour changes the issue asks to be stated
explicitly; #556 needs neither.

### Test design

New module `apps/m3u/tests/test_file_reupload.py`, one class `M3UFileReuploadTests(TestCase)`, driving
`PATCH /api/m3u/accounts/<id>/` with a multipart upload through `APIClient` as an admin
(`user_level=10`). The view hardcodes `/data/uploads/m3us` at `:163` and `:167`; the test redirects
`apps.m3u.api_views.safe_upload_path` into a `tempfile.mkdtemp()` directory (resolved with `realpath`,
so paths compare equal on hosts where `/tmp` is a symlink) and makes `apps.m3u.api_views.os.makedirs`
a no-op. That second patch is process-wide for the test's duration (`apps.m3u.api_views.os` is the
`os` module); the module comment says so. The account is created with

## PR 2 — #554: `_redact_url` puts part of a credential where the host should be

### Root cause

`_redact_url` (`apps/timeshift/views.py:3738-3746`) is the local helper that reduces a provider URL to
`scheme://host/...` before it is logged. It finds the host with string splits:

```python
    scheme, rest = url.split("://", 1)        # :3742
    if "@" in rest:                            # :3743
        rest = rest.split("@", 1)[1]           # :3744  FIRST "@" anywhere after the scheme
    host = rest.split("/", 1)[0]               # :3745  stops at "/" only
```

`rest` is the whole remainder of the URL, not its authority, and the split takes the **first** `@` in
it. Its callers log the result at WARNING, ERROR and DEBUG (`:3344-3348`, `:3351-3355`, `:3363-3369`,
`:3399-3407`, `:3432-3435`) and store it in the catch-up channel's metadata (`:3121`,
`ChannelMetadataField.URL`). Each log call carries a `credential-logging: ignore` marker that trusts
this helper, so `scripts/check_credential_logging.py` cannot see a leak through it.

How a URL with an unexpected `@` or no path arrives: an operator-entered XC `server_url` with userinfo
(the builders prefix it verbatim, `apps/timeshift/helpers.py:422`, `:434`); a provider redirect's
`response.url`, assigned to `last_url` at `:3360` and logged at `:3435`; and a cached CDN final URL
(the `cached_final` branch, `:3343-3348`), which is provider-supplied. The URLs Dispatcharr builds
itself are safe: `build_timeshift_url_format_a`/`_b` (`apps/timeshift/helpers.py:418-440`) encode the
XC username and password with `quote(..., safe='')`, which turns `@` into `%40`.

### Fix: last `@` of urlsplit's authority, and mask what is ambiguous

Appendix 554-A rewrites the helper's body and nothing else in its contract:

```python
    if not url or "://" not in url:
        return url
    try:
        parts = urlsplit(url)
    except ValueError:
        return REDACTED
    if "@" in parts.path or "@" in parts.query or "@" in parts.fragment:
        return REDACTED
    host = parts.netloc.rpartition("@")[2]
    return f"{parts.scheme}://{host}/..."
```

- **The authority is urlsplit's netloc**, which ends at the first `/`, `?` or `#`, so a query with no
  path is no longer part of the "host".
- **The host is what follows its last `@`**: the rule `urlsplit` (`.hostname`), `urllib3.parse_url`
  (what requests dials) and `dispatcharr.utils._redact_netloc` (`dispatcharr/utils.py:124-129`,
  `netloc.rpartition("@")`) all apply.
- **An `@` after the authority masks the URL whole.** With a `/`, `?` or `#` unencoded in a password,
  urlsplit ends the netloc inside the userinfo: `http://usr0:12/tail9@example.invalid/x` has netloc
  `usr0:12`, which reads as host `usr0`, port `12`. The seed helper happens to get that case right
  (first `@` of the remainder), so a pure urlsplit rule would be a regression; the `@` that follows the
  netloc is the only sign of it, and there is no reliable way to tell `http://usr0:12/tail9@host/` from
  `http://host:12/a@b/`, so both are masked. A legitimate URL with an `@` in its path or query loses its
  host in the log line and nothing else.
- **Never raises.** `urlsplit` raises `ValueError` on a malformed IPv6 literal and on a netloc that
  NFKC-normalises to a delimiter (the fullwidth `@` above); both return `REDACTED` (`"***"`,
  `dispatcharr/utils.py:59`), the mask `redact_url` already uses.
- **Unchanged:** `None`, `""` and any string without `://` are returned as given (the existing
  `test_passes_through_non_urls` pins it); the port is kept; the output shape stays `scheme://host/...`.
  The scheme is now urlsplit's, which is lowercased.
- **The five stale marker comments** (`(:3621)` at `:3345`, `:3352`, `:3364`, `:3433` and `(:3580)` at
  `:3400`, both dead line references; the helper is at `:3738`) say `(below)` instead of a line number
  that drifts again. The reason text after `credential-logging: ignore -` is kept, so the checker still
  accepts each marker.

**Why not the issue's `.hostname` + `.port`.** It leaks the username and the head of the password on
the slash case (BC-554-4 below: `http://usr0:12/...`) and lowercases or unbrackets the host for no gain.

**Why not delegate to `dispatcharr.utils.redact_url`.** Two reasons. It keeps the path and query,
masking only the shapes it knows, where this helper's contract is `scheme://host/...`, which the stats
metadata at `:3121` also relies on. And it has its own version of the slash case (§ Other redaction
helpers). The fix reuses its host rule (last `@` of the netloc), not the function.

## PR 3 — #555: strict mode admits `100.64.0.0/10`

### Root cause

`validate_outbound_http_url` (`core/http_security.py:14-146`) classifies each resolved address by
category (`:124-143`): loopback (refused unless `allow_loopback`), unspecified, multicast and link-local
(always refused), private (refused unless `allow_private`), reserved (always refused). It never asks
`is_global`. An address outside every category passes in strict mode (`allow_private=False`).

Enumerated under Python 3.13.15 (the container's; `.python-version` is `3.13`), one address per IPv4
`/16`, plus every `192.0.0.x` and a set of IPv6 forms: the addresses that are **not** global and in
**none** of the six categories are exactly `100.64.0.0/10` (RFC 6598 shared address space: carrier-grade
NAT, Tailscale's tailnet range) and its IPv4-mapped form `::ffff:100.64.0.0/106`. Every other non-global
range the sweep found is already private or reserved (`192.0.0.0/24` apart from `.9`/`.10`,
`192.0.2.0/24`, `198.18.0.0/15`, `240.0.0.0/4`, `64:ff9b:1::/48`, `2001::/23`, `2002::/16`, …), and the
NAT64 prefix `64:ff9b::/96` is reserved, so it is refused even when it embeds a global address.

Strict-mode callers are the plugin fetches only: `_validate_fetch_url` and `_fetch`
(`apps/plugins/api_views.py:84-100`), reached from `_fetch_manifest` (`:787-791`; called at `:826`,
`:871`, `:996` and by the Celery task `apps/plugins/tasks.py:20`) and from the install path
(`:1151`, `:1161`, `:1277`, `:1281`). The views are admin-only POSTs. The one lenient caller,
`core/image_proxy.py:116` (`allow_private=True`), is unaffected by design (below).

- **Python-version dependence.** `is_global` and `is_private` were revised in 3.12.4/3.13 (for example,

## Open questions for the owner

1. **An allow-list escape hatch for plugin fetches on a tailnet or CGNAT (#555).** *Recommendation: no,
   not in this PR.* Strict mode has never had an escape hatch for private addresses: a plugin
   repository on `192.168.x.x` is refused today, and a tailnet host is the same trust class. Adding one
   for `100.64/10` alone would make a tailnet more trusted than a LAN. If self-hosted plugin repositories
   on a private network are wanted, that is one operator setting that switches the plugin fetches to
   `allow_private=True` (covering LAN and tailnet together), filed as its own issue. Operators behind
   CGNAT are unaffected: CGNAT is their own address, and public hostnames still resolve to global ones.
2. **The slash-in-userinfo gap in `dispatcharr.utils.redact_url` and `relay/redact.Line`.** *Recommendation:
   file one low-priority `type:security` issue covering both, and leave them out of #554's PR.* With an
   unencoded `/` in a password, `redact_url` returns the URL verbatim and `redact.Line` keeps
   `usr0:12` as the "host" (§ PR 2, Other redaction helpers). Exposure needs a stored credential with an
   unencoded `/`, and the URL cannot be dialled, so it surfaces only on failure paths. Each helper has its
   own contract (`redact_url` keeps the path; `redact.Line` is the Go module's single redactor with its
   own tests), so the fix is two separate designs, not a line in this PR.
3. **#556's two neighbours.** *Recommendation: file one `type:correctness` issue, not fixed here.* (a)
   `create()` (`apps/m3u/api_views.py:92-105`) stores uploads by basename only, so two accounts that
   upload `playlist.m3u` share one file and the second overwrites the first's; a later re-upload of
   either under a new name then deletes the other's file. (b) `update()` removes the previous file before
   `super().update()` validates (`:188-189` vs `:192`), so a 400 leaves the account pointing at a deleted file.
   The fix for both is a per-account stored name (for example prefixing the account id, or a counter as
   `apps/backups/api_views.py:282-290` does) and moving the removal after a successful save: a behaviour
   change the issue asks to be stated explicitly.
